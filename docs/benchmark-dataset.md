# MEVA Benchmark Dataset Reference

This is a quick reference for the three benchmark datasets. For the
metrics computed from them, see `docs/benchmarking.md`.

## v0.1 vs v0.2 vs v0.3

| | `v0.1/cases.json` | `v0.2/cases.json` | `v0.3/cases.json` |
|---|---|---|---|
| Purpose | Quick smoke test | Structured benchmark | Comparison-ready benchmark |
| Case count | 12 | 40 | 56 |
| Synthetic patients used | 3 | 3 | 18 |
| Evidence format | Loose strings | Structured `expected_evidence_facts` | Structured, plus `attribute`-level regression cases |
| Case types | All effectively AGENT | 37 AGENT, 3 VERIFIER_CHALLENGE | 52 AGENT, 4 VERIFIER_CHALLENGE |
| Difficulty label | none | none | `simple`/`multi_fact`/`multi_tool`/`negative`/`error` |
| Manifest | none | `v0.2/manifest.json` | `v0.3/manifest.json` |

v0.1 and v0.2 are never modified by later stages — each stays exactly
what it was when created. v0.1 remains the fast sanity check
(`python3 examples/run_benchmark.py`, default 3 cases); v0.3 is the
current recommended dataset for anything beyond a quick smoke test.

## AGENT cases

Run the real local model through MEVA's full pipeline (tool selection →
evidence retrieval → structured claims → deterministic verification).
This is what tests the model.

## VERIFIER_CHALLENGE cases

Skip the live model and feed a deliberately wrong, hand-written claim
straight into MEVA's verifier. A live model can't reliably be told to
answer incorrectly "on demand" in a reproducible way, so these cases
test MEVA's verification logic directly instead. **Never report these
as evidence of a model's performance** — `aggregate_metrics()` keeps
them in a completely separate `verifier_challenge` section for exactly
this reason.

v0.2's three challenges cover one case for each non-trivial status:

- `verifier-challenge-01` — false "no allergies" claim → expects `CONTRADICTED`
- `verifier-challenge-02` — false "Aspirin allergy" claim (not recorded) → expects `UNSUPPORTED`
- `verifier-challenge-03` — a clinical-interpretation claim ("this blood pressure is dangerously high") → expects `UNVERIFIABLE`

v0.3 adds a fourth, proving the Stage 7B.5 attribute verifier catches a
wrong metadata claim too:

- `verifier-challenge-04` — false "Fish allergy has high criticality" claim (real value is "low") → expects `CONTRADICTED`

## Attribute-level ("multi_fact") cases

v0.3 adds 4 `multi_fact` difficulty cases (`allergy-06`, `allergy-07`,
`medication-07`, `condition-06`) that ask about both an item's name and
one of its metadata fields (criticality, clinical status, status). These
are the direct regression tests for the Stage 7B verifier-coverage fix —
see `docs/evidence-verification.md`, "Attribute-level evidence."

## Tool metrics summary

See `docs/benchmarking.md` for exact formulas. In short:

- **Tool recall** — did the model call every tool it needed?
- **Tool precision** — of the tools it called, how many were actually needed?
- **Exact match** — did it call exactly the needed tools, no more, no less?
- **Over-calling** — how often did it call tools beyond what was needed? (tracked, not penalized)
- **Duplicate calls** — how often did it call the *same* tool more than once? (tracked, not penalized)

## Evidence recall

Only computed for cases with `expected_evidence_facts`. Checks whether
each expected fact (e.g. a specific allergy name tied to a specific
FHIR resource ID) actually appeared in what the tools returned during
that run — using MEVA's existing conservative normalizer, never fuzzy
medical matching.

## Where the data comes from

Every AGENT case's `patient_id` and `expected_evidence_facts` were
generated by directly querying MEVA's own tools against the real
Synthea bundles in `data/synthetic/synthea/` (see
`examples/inspect_benchmark_data.py` to reproduce this) — never typed
in by hand from memory. `src/meva/benchmark/validator.py` re-checks
every fact against the live bundle before the dataset can be used,
catching drift if the fixture data ever changes.

## Duplicate detection

`src/meva/benchmark/validator.py` fingerprints every case
deterministically (patient + category + expected tools + expected
evidence resource IDs + normalized question text). An exact match to
another case fails validation; a case with identical question wording
but a different fingerprint only produces a warning. No embeddings or
LLM involved — see `docs/benchmarking.md`.

## Limitations

- All three datasets are **engineering benchmark samples** — not
  sufficient for clinical validation or statistical claims about model
  reliability. See each version's `manifest.json` → `"limitations"`.
- Even in v0.3 (18 patients), only one synthetic patient has any
  recorded allergies, so all 8 allergy cases necessarily involve that
  one patient — documented rather than padded with invented facts.
  Medication and condition cases have much better patient spread.
